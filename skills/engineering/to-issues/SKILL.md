# To Issues

Break a PRD into independently-grabbable issues using vertical slices (tracer bullets).

The skill takes one argument: `<slug>` (kebab-case). If invoked without a slug, error with:

> Pass a slug: `/to-issues <slug>`. List active slugs with `gh issue list --label kind:prd --state open`.

The GitHub workflow and triage-role label mapping must have been provided by `/setup-repo-skills`. Stop and ask the user to run it if either `docs/agents/issue-tracker.md` or `docs/agents/triage-labels.md` is missing.

## Process

### 1. Gather context

Find the PRD tracker issue:

```
gh issue list --label "prd:<slug>" --label "kind:prd" --state open --json number,body
```

Expect exactly one result.

- Zero results → abort: "No PRD tracker found for `<slug>`. Run `/to-prd <slug>` first."
- More than one → abort: "Multiple candidates: #N, #M. Resolve manually before re-running."

Read the PRD body from this issue. Hold the issue number and the numbered user stories — will be used later.

### 2. Explore the codebase (optional)

If you have not already explored the codebase, do so to understand the current state of the code. Issue titles and descriptions should use the project's domain glossary vocabulary, and respect ADRs in the area you're touching.

### 3. Draft vertical slices

Break the PRD into **tracer bullet** issues. Each issue is a thin vertical slice that cuts through ALL integration layers end-to-end, NOT a horizontal slice of one layer.

<vertical-slice-rules>
- Each slice delivers a narrow but COMPLETE path through every layer (schema, API, UI, tests)
- A completed slice is demoable or verifiable on its own
- Prefer many thin slices over few thick ones
</vertical-slice-rules>

### 4. Quiz the user

Present the proposed breakdown as a numbered list. For each slice, show:

- **Title**: short descriptive name
- **Blocked by**: which other slices (if any) must complete first
- **Covers user stories**: PRD story numbers this slice implements (e.g. `<N>, <M>, ...`) if the PRD has them

Ask the user:

- Does the granularity feel right? (too coarse / too fine)
- Are the dependency relationships correct?
- Are all PRD user stories covered across the slices?
- Should any slices be merged or split further?

Iterate until the user approves the breakdown.

### 5. Publish

Publish in **dependency order** (blockers first) so `## Blocked by` references resolve to real `#N`.

Read the actual GitHub label mapped from the canonical `needs-triage` role in `docs/agents/triage-labels.md`.

For each approved slice, in order:

1. Render the issue body using the `<issue-template>` at the bottom of this file.
2. Write the body via the `Write` tool to `/tmp/to-issues-<slug>-<N>.md` where `<N>` is a counter (1, 2, 3, …). Never use `--body` inline.
3. Create the issue:
   ```
   gh issue create \
     --title "<slice title>" \
     --body-file /tmp/to-issues-<slug>-<N>.md \
     --label "prd:<slug>" \
     --label "<actual needs-triage label>"
   ```
4. Capture the returned issue number for use in later slices' `## Blocked by` sections.

Do NOT close or modify the PRD tracker issue.

<issue-template>

> _This was generated by AI during issue authoring._

## Parent

#<PRD tracker issue number>

## What to build

A concise description of this vertical slice. Describe the end-to-end behavior, not layer-by-layer implementation.

Avoid specific file paths or code snippets — they go stale fast. Exception: if a prototype produced a snippet that encodes a decision more precisely than prose can (state machine, reducer, schema, type shape), inline it here and note briefly that it came from a prototype. Trim to the decision-rich parts — not a working demo, just the important bits.

## User stories

Covers stories <N>, <M>, ... in #<PRD tracker issue number>.

Reference the numbered user stories from the PRD body by plain number. Use `None` if the slice is pure infrastructure with no direct user-facing value.

## Acceptance criteria

- [ ] Criterion 1
- [ ] Criterion 2
- [ ] Criterion 3

Each criterion must:

- Use imperative voice ("Add X", "Replace Y with Z" — not "X should be Y").
- Reference specific code (file path, symbol name, or interface) where applicable.
- State the success condition.

## Blocked by

Comma-separated list of `#<N>` references to blocking issues, or literal `None` if no blockers.

`## Blocked by` is parsed by downstream tooling.

</issue-template>
